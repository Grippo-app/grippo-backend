# Протокол оркестрации

## Результат и порядок

Исследование → план → законченный срез → самопроверка автора → проверки →
независимое ревью → исправления → повторная проверка/ревью → интеграция.
Изменённый код, успешная компиляция или отдельное APPROVE сами по себе
не доказывают выполнение задачи.

До изменений прочитай AGENTS, git status/diff и профильный skill. Проследи
controller → service → provider/entity → response. Установи исходный контракт,
владельца данных, границу транзакции и неизвестные условия. Не подключай
AppModule/БД для обычного исследования.

Для существенной работы зафиксируй цель, критерии готовности каждого среза,
файлы/автора, зависимости и способы проверки. Используй документ задачи;
незавершённый план другой работы не перезаписывай. Маленькая правка не требует
отдельного плана, команды из всех ролей или нового журнала.

## Граница изменений задачи и Git index

Перед первой правкой различи исходные staged, unstaged и относящиеся к задаче
untracked изменения и свой вклад. Reviewer передавай diff относительно этого
исходного состояния: общий diff от HEAD может включать чужую работу.
При пересечении в одном файле проверяй отдельные hunks, а не только paths.

Если commit входит в задачу, включай только её изменения и проверь весь staged
diff перед commit. При чужом index не используй безусловные `git add .` или
`git commit -a`; чужие hunks не очищай и не переиндексируй автоматически.
Если вклад нельзя надёжно отделить, согласуй границу пересечения до его записи
или индексации; независимую работу продолжай. Пользовательские файлы сохраняются.

## Роли и выбор автора

Профили наследуют модель и разрешения сессии. Read-only — ограничение задания,
а не отдельная OS sandbox.

| Agent | Ответственность |
|---|---|
| [grippo-orchestrator](../../../../.codex/agents/grippo-orchestrator.toml) | План, владельцы файлов, делегирование, интеграция и итоговые результаты |
| [grippo-architect](../../../../.codex/agents/grippo-architect.toml) | Исследование связей вызовов, DI, модулей и контрактов; без правки файлов |
| [grippo-domain-specialist](../../../../.codex/agents/grippo-domain-specialist.toml) | Entities, trainings, catalog, dictionaries, metrics; анализ или назначенный срез |
| [grippo-identity-specialist](../../../../.codex/agents/grippo-identity-specialist.toml) | Auth/users/admin/i18n/weight/push; анализ или назначенный срез |
| [grippo-operations-specialist](../../../../.codex/agents/grippo-operations-specialist.toml) | Scripts/Docker/env/SSH/recovery; анализ или явно назначенная работа |
| [grippo-implementer](../../../../.codex/agents/grippo-implementer.toml) | Небольшой срез по определённому контракту, самопроверка и передача результата |
| [grippo-verifier](../../../../.codex/agents/grippo-verifier.toml) | Независимые безопасные проверки; реализацию не меняет |
| [grippo-reviewer](../../../../.codex/agents/grippo-reviewer.toml) | Независимое ревью без правки файлов и проверка исправленных замечаний |

Выбирай профильного специалиста, когда нужно предметное решение: например,
формула метрики, linking identity, каскад удаления или порядок восстановления.
Он может сам реализовать назначенный срез. Implementer подходит для небольшой
правки, когда контракт и способ изменения уже определены. Одна задача не требует
обоих: при необходимости специалист исследует вопрос, а назначенный автор пишет код.

Выбирай минимальный состав. У общего файла один автор. Независимые исследования
и файлы можно вести параллельно; общий контракт сначала согласуй. Изменения
схемы/зависимостей, один деплой или общая изменяемая тестовая БД требуют
последовательной работы. Перед правкой перечитай файл и сохрани чужие изменения.

Если выбрать custom role нельзя, передай агенту роль и нужный skill текстом.
Если subagents недоступны, выполни отдельные проходы сам и честно укажи
отсутствие независимого reviewer.

## Передача задачи

Передай агенту только нужный контекст:

- исходный запрос, ожидаемую разницу и критерии готовности;
- источники, согласованный контракт и зависимости;
- режим исследования/реализации/проверки/ревью, собственные и общие файлы;
- допустимые побочные эффекты и изолированное окружение;
- ожидаемый результат: замечания/diff, источники, проверки и ограничения.

Для эксплуатационной работы также передай исходное прямое разрешение человека,
цель/revision/попытку и сведения о backup. Назначение другим агентом само по себе
не разрешает деплой. Reviewer получает исходный запрос, текущий diff, исходное
состояние и результаты проверок без подсказки ожидаемого вердикта.

## Возобновление работы и новые вводные

После паузы, восстановления контекста или передачи задачи перечитай актуальную
цель, критерии готовности, решения и незавершённые шаги. Сверь текущую revision,
status/diff, результаты проверок/ревью и состояние исполнителей с исходным
состоянием задачи. Прежние результаты применимы только к проверенному состоянию
и объёму работы.

Новые ограничения/отмену доведи до всех затронутых авторов и reviewers. Останови
работу, ставшую вне задачи, и согласуй владельцев файлов/зависимости до её
продолжения. Поздний результат агента проверяй по новым вводным перед интеграцией.
Действующая авторизация сохраняется в исходных границах, пока пользователь их
не изменил; сам перерыв не требует повторного разрешения той же работы.

Для незавершённой внешней операции сначала установи фактический статус:
отсутствие финального вывода не доказывает остановку или rollback. Не повторяй
запись ради получения ответа; проверь исход и правила повторов. Для
эксплуатационных действий дополнительно сверяй цель/revision/попытку с политикой
деплоя ниже; новые вводные не расширяют выданное разрешение.

## Реализация и проверка

Один срез завершает пользовательский путь, а не добавляет абстракции ради плана.
Автор читает итоговый diff и проверяет контракт, ownership, отсутствующие/null/
пустые/повторяющиеся данные, транзакции, FK, числа, даты, историю и локаль.
Предметные сценарии находятся в профильном skill; общий
[review protocol](../../grippo-review/references/review-protocol.md) не копируй.

Выбирай проверки по [checks](../../grippo-verification/references/checks.md).
Компиляция не доказывает поведение при выполнении. Fixtures с подменёнными
providers проверяют только пути своего стенда, включая HTTP/controller flow;
они не подтверждают реальные связи БД/auth/providers. Отсутствие допустимой
среды интеграции — ограничение, не PASS.

Для каждого применимого замечания: подтверди причину → исправь → повтори
затронутые проверки → передай актуальный diff reviewer → получи проверку
исправления. При споре решают исходники и воспроизведение, а не число голосов.
Существующую проблему вне задачи запиши отдельно, не расширяя работу.
Если исправление зависит от внешнего доступа/решения, подготовь проверяемый
результат и назови незавершённый шаг. Лимит попыток не превращает дефект в готовую задачу.

После интеграции сверь результаты всех участников, imports/контракты и final diff.
Изменение после APPROVE требует повторного ревью затронутой части. Завершай,
когда критерии выполнены, применимые блокирующие замечания закрыты и проверки
актуальны; в финале кратко укажи результат и существенные ограничения.

## Граница эксплуатации

Деплой не является продолжением готовой локальной работы. Действует
[deployment-policy](../../grippo-operations/references/deployment-policy.md):
прямое разрешение человека на каждую конкретную попытку и новый scripts/dump.sh
с проверенным backup до выкладки. SSH, dump-only, ревью и поручение агента
его не заменяют. После сбоя/обрыва — диагностика, сохранение good copy,
новое согласование; автоматический повтор запрещён.
