# Подготовка содержания

## Контекст и канон

В `canon.md` зафиксируй название/синонимы, отличие от ближайших записей,
снаряд/геометрию машины, опоры, положение тела, хват/стойку, сторону/режим,
сопротивление/помощь, начало/конец ROM, основные действия и вход/выход.
Отдельно запиши количество снарядов и как вводится вес, если это влияет на
клиента. Не выводи это из плоского списка equipment refs.

Используй [модель упражнения](../../grippo-exercise-audit/references/exercise-model.md).
Доступное фото/видео действительно просмотри; URL не доказывает просмотр.
В evidence запиши фактически просмотренные timestamps/фазы, setup, траекторию
и точки контакта. Transcript/title не подтверждают видимую геометрию. Если
видео недоступно, отметь это и сам ищи доступную демонстрацию того же канона;
не симулируй просмотр и не подменяй вариант похожим роликом.
Техника, название, текст и изображение должны задавать один вариант.
Если у общего названия есть разные существенные установки, задай конкретный
канон, а не смесь нескольких вариантов. Альтернативы можно предложить,
но не смешивать их в одной карточке для удобства заполнения enum.

## Evidence и решения продукта

По [research program](../../grippo-exercise-audit/references/research-program.md)
сформулируй существенные claims, ищи и открывай подходящие первоисточники,
включая противоречащие. Researcher передаёт источники и реальные методы/
результаты, evidence analyst независимо сверяет их и применимость к канону.
Для точной машины полезен официальный manual. Нет произвольного минимума
статей; нехватку прямых данных сохраняй как ограничение.

Самостоятельный поиск включает демонстрацию точного варианта, описание/manual
оборудования, если оно специфично, и первичные исследования для существенных
эмпирических claims. Найденное видео помогает установить наблюдаемую технику;
оно не становится научным доказательством процентов или эффективности.

В `evidence.md` достаточно claim → источник/локатор/прочитанный объём →
результат → перенос на вариант → решение/неопределённость. Поисковый журнал
показывает фактические действия. Общие знания допустимы для гипотезы;
не выдумывай чтение статьи или научное основание процентов.

Установи действующие правила продукта: смысл muscle percentages и их
знаменатель, рубрику difficulty/category, коэффициент собственной массы и
семантику equipment. Следуй принятым решениям. Если их нет, подготовь
конкретную редакционную модель и предложение значений с основаниями; доведи
независимые части до готовности и запроси только влияющий на запись выбор.
Не скрывай этот выбор в нормировке к 100 или слове «научно».

## Поля карточки

| Поле / владелец | Что подготовить и проверить |
|---|---|
| Техника / coach + biomechanics | Setup → контролируемое повторение → конечное положение/возврат и завершение. Основные cues, которые меняют выполнение, естественно входят в description. Не добавляй в API вымышленные tutorial/cues поля. |
| Muscle map / muscle-map | Сначала качественные роли, затем полный вектор UUID+целые проценты по принятой редакционной модели, сумма 100 и основание каждого веса. Target изометрия возможна. Не нормируй EMG в проценты каталога. |
| Category, forceType / biomechanics | Значение доступного enum с объяснением через основные действия и сопротивление. При непредставимом варианте верни проблему контракта; случайную метку ради JSON не выбирай. |
| Experience / difficulty | Техническая установка, координация, траектория/контроль, сравнимые anchors и ближайший уровень. Сила, RPE и персональная readiness отдельно. |
| Equipment, weightType, components / equipment | Реальные UUID; необходимые опоры/снаряды; null/optional/required каналы и обоснованный body multiplier. Уточни, что измеряет коэффициент. Нет правила «вся свободная нагрузка → одна и та же карта». |
| Имена и описания / localization | Все фактические target languages; один канон, анатомия, сторона, помощь, модальность и одинаковые содержательные действия. Base English = en. |

Инварианты/ограничения текущей модели — в
[catalog policies](../../grippo-exercise-audit/references/catalog-policies.md)
и [актуальном контракте](../../grippo-domain-data/references/catalog-and-dictionaries.md).
Их старые списки языков могут отставать: проверяй
[`SUPPORTED_LANGUAGES`](../../../../src/i18n/i18n.types.ts) и target отдельно.
Нет CRUD справочников: отсутствующий тип/UUID означает запрос на отдельное
расширение, не выдуманный ID или подмена похожим инвентарём.
При отсутствии нужной экипировки обязательно сообщи пользователю название,
необходимость и блокируемые поля. Equipment и его отдельную картинку не
создавай автоматически: сейчас эту картинку делает/предоставляет пользователь.
Следуй [правилу missing equipment](preview-and-approval.md). Локальный preview
можно подготовить с явно pending позицией; публикация/создание пакета ждут
решения и реального ref, `equipmentRefs: []` отсутствие не маскирует.

## Переводы и редакционный brief

Сначала согласуй смысл исходного текста; ошибочный English не становится
эталоном. Название коротко различает вариант; description позволяет его
воспроизвести без рекламных обещаний и необоснованных абсолютных углов.
Для технических действий подойдут короткие последовательные предложения.
Не устанавливай универсальную длину или число предложений без UI ограничения.

`ua` — API code проекта. `pt-BR` и `pt-PT`, если поддерживаются целью,
получают отдельные естественные тексты; механическое дублирование не является
их проверкой. Не полагайся на public fallback для полноты переводов.

Сведение AI-прохода может использовать такой контракт:

```text
Вход: canon version, реальные dictionaries и target languages, принятые
редакционные правила, evidence с ограничениями, черновик карточки.
Задача: подготовить только назначенные поля. Сохрани канон и все чужие поля.
Не изобретай UUID/источники/проценты измеренной активации. Верни конкретные
значения, основания/неопределённость отдельно от JSON и конфликтующие inputs.
Выход: поля в editor shape + field-level rationale + pending decisions.
```

Ведущий собирает `draft.json`, источники и решения. Статус каждого направления
должен отражать реально выполненную работу. Если нужна передача reviewer,
он получает исходные основания и изображение, а не только уверенный вывод AI.

На стадии частичной подготовки `draft.json` может быть неполным: неизвестные
поля опускай, отсутствующие известные equipment refs представлены `[]` только
когда отсутствие оборудования установлено. Не придумывай UUID/URL и не
добавляй служебные pending-поля внутрь draft. Качественные роли, нерешённые
числа и ссылки на ещё не сопоставленный словарь храни отдельно; `manifest.json`
перечисляет незаполненные JSON paths и причины. Helper запускается для
полного content draft: preview mode берёт только будущий imageUrl из media plan,
а неизвестные мышцы/оборудование/числа/переводы не заполняет автоматически.
Для такого частичного черновика он намеренно не выдаёт готовый пакет.
