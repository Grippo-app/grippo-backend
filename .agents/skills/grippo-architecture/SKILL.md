# Архитектура Grippo

Перед изменением найди путь controller → service → provider/entity и сверь
его с соседним кодом.

- [architecture.md](references/architecture.md): bootstrap, слои, модульные связи,
  DI, общие сервисы и интеграции. Читать при добавлении feature или изменении
  связей между модулями.
- [conventions.md](references/conventions.md): наблюдаемый кодстайл и правила
  небольшого изменения. Читать перед написанием кода.
- [source-map.md](references/source-map.md): полный индекс исходников и конфигов
  с ответственными skills. Использовать для поиска, не загружать всё сразу.

## Порядок работы

1. Установи входную точку, вызывающие стороны и контракт ответа/ошибок.
2. Найди нужный feature module в source-map; проверь его imports/exports.
3. Если нужен repository, найди существующий строковый token и `DatabaseModule`.
   При новой entity сначала оцени влияние на схему, затем необходимость token:
   сущность, используемая только в транзакции, может работать через manager
   без отдельного provider.
4. Сохраняй структуру по feature modules; не создавай новые слои ради одного endpoint.
   В admin используй экспортируемые сервисы, подключая их модули.
5. Оцени влияние на DTO, Swagger, global pipe, локализацию, проверку владельца и БД.
6. Сделай небольшое законченное изменение; проверь DI, границы транзакций,
   совместимость формата ответа и TypeScript без запуска приложения.
7. Обнови только затронутые references, если изменилась описанная архитектура.

## Self-review

Проверь, что сервис доступен через imports/exports модулей, а новый token
зарегистрирован там, где нужен. Запросы внутри транзакции используют её manager;
request DTO проходит валидацию; ответ не раскрывает закрытые поля entity.
Новая абстракция должна решать повторяющуюся задачу. Известную ошибку не объявляй
нормой и не исправляй заодно без связи с запросом.
