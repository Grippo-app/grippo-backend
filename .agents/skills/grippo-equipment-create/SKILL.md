# Grippo: добавление оборудования

Преврати свободное описание или переданный файл в проверяемый план добавления
отдельного оборудования. Если поручена реализация, выполни локальные изменения
и проверки по этому плану. Запрос только на план заканчивается планом;
готовый mobile-код не означает готовый серверный каталог.

Прочитай AGENTS, [domain-data](../grippo-domain-data/SKILL.md) и актуальные
[equipment enum](../../../src/lib/equipment.enum.ts),
[entity](../../../src/entities/equipments.entity.ts),
[group entity](../../../src/entities/equipment-groups.entity.ts),
[service](../../../src/modules/equipments/equipments.service.ts),
[response](../../../src/modules/equipments/dto/equipment-response.ts) и
[DB config](../../../src/database/database.service.ts).
Остальной код открывай по затронутым потребителям, а не весь проект.

## Разбор входа

Прочитай приложенный текст целиком. Сведи в контракт:

- Название, геометрию/setup и отличие от существующего оборудования;
  означает ли запрос новую сущность, вариант или переименование.
- API `type` и основание его выбора/подтверждения, group `type`, согласованное
  серверное `name`, локализованные названия и смысл вводимого веса.
- Существующие UUID, названия и связи, которые требуется сохранить.
- Клиентский проект/revision, domain/UI enum, mapping, ресурсы, preview IDs
  и состояние реализации, если они переданы.
- Желаемый результат: план, локальная реализация, подготовка SQL или конкретная
  внешняя операция; выбранную среду и границы доступа, если они заданы.

Различай подтверждённые решения владельца, утверждения входного текста,
проверенные факты текущего кода/среды и неизвестное. Не выводи API key из
`enum.name`, перевода или имени иконки. Если ключ не задан, предложи явный
стабильный key и вынеси существенную неоднозначность в открытый вопрос.
Уже подтверждённый ключ не согласовывай повторно.

UUID preview не является серверным UUID. UUID оборудования и группы, имя/schema
PostgreSQL enum и target указывай только с проверенным источником; иначе пиши
«неизвестно» и укажи, на каком этапе это выясняется. Неизвестная среда не мешает
плану и локальной подготовке. Не требуй заполнения всех полей от пользователя,
если доступные исходники дают ответ или вопрос нужен только для будущей операции.

## Исследование и решение

1. Сверь Git status/diff и текущие исходники с переданной revision. Сохрани
   прежние изменения. Найди все потребители enum, хранение/выдачу справочника,
   exclusions по UUID и refs упражнений. Не запускай AppModule ради исследования.
2. Установи фактический механизм наполнения каталога и обновления схемы.
   В текущем проекте нет equipment CRUD/seed и настроенных migrations;
   для ручных schema changes есть `scripts/sql`. Перепроверь это перед изменением.
   TS enum не добавляет label в существующий PostgreSQL enum и не создаёт строку.
3. Для разрешённой цели проверь metadata и существующий каталог. Пока цель или
   доступ не заданы, подготовь preflight с ожидаемыми проверками, без подключения.
   Нужны реальный тип столбца/enum consumers, ровно одна ожидаемая группа,
   существующая запись по type, дубли и конфликты имён/группы. Отсутствующую
   группу не создавай попутно без включения её в контракт и план.
4. Сверь доступный mobile: точный wire key, domain/UI mapping и обработку
   неизвестного type по пути decode → domain → кеш. Различай working tree,
   commit/tag, release artifact и установленную версию. Проверяй реальные
   supported/released builds, когда это нужно для публикации; отсутствие этих
   данных запиши как будущую зависимость, продолжая локальную работу.
5. Сохрани текущий response contract. Сейчас оборудование возвращает
   `id`, `name`, `type`, `equipmentGroupId`, `createdAt`, `updatedAt`;
   group ID должен совпадать с родительской группой. `name` хранится одной
   строкой, локализация mobile не требует новых backend полей.

## План и локальная подготовка

Сохрани план с checklist в заданном пользователем месте или по соглашению
проекта; по умолчанию достаточно одного `tasks/plan.md`. Отдельный todo/report
создавай только для существующего потребителя, без дублирования плана.
Разовые отчёты и evidence храни там же локально; не создавай постоянный
`docs/*` на каждую запись оборудования. Документацию добавляй в Git, когда
пользователь поручил её как поддерживаемый результат.
Чужой незавершённый план не перезаписывай. Для каждой задачи укажи результат,
зависимости, владельца/файлы, критерии приёмки и проверку. Используй
[orchestrator](../grippo-orchestrator/SKILL.md) для распределения работы.

Раздели в плане текущий контракт/неизвестное, локальный срез, будущую проверку
целевой БД, совместимость клиентов и отдельно разрешаемое применение/deploy.
Уже подготовленный код/SQL помечай как подготовленный с фактическим evidence,
а применение — только как применённое при подтверждении в нужной среде.
Не помечай весь план готовым по одной компиляции.

Для порученной реализации следуй существующим соглашениям:

- Добавь enum и необходимые потребители; не вводи новый endpoint, migration
  framework или автоматический bootstrap ради одной записи.
- Подготовь additive schema step с реальным или проверяемым через metadata
  enum name. В PostgreSQL 15 COMMIT добавления label предшествует data step.
- Data step сохраняет UUID и timestamps корректной существующей записи;
  при отсутствии создаёт собственный серверный UUID. Дубли и конфликты
  выявляются явно, без переименования или исправления чужих строк.
  Идемпотентность должна учитывать параллельные запуски, а не только повтор.
- Сохрани старые equipment UUID, exclusions и exercise refs. Новое оборудование
  не назначается упражнениям автоматически: отдельные UUID references карточки
  не являются правилом взаимозаменяемости тренажёров. Порученные изменения refs
  выдели в отдельную задачу по конкретным карточкам.
- По [checks](../grippo-verification/references/checks.md) выполни применимые
  проверки и актуализируй существующую PostgreSQL suite для schema/data среза:
  повтор/UUID/timestamps, конфликты, locks, старые связи, public response и
  независимые exclusions. Новые постоянные tests вне существующей suite —
  по AGENTS. После self-review нужен [независимый review](../grippo-review/SKILL.md).

## Срок жизни SQL

Применяй [правила завершения и очистки](../grippo-orchestrator/references/workflow.md#завершение-и-очистка).
Разовые SQL-пробы не оставляй в `scripts/sql`; подготовленный пакет будущего
применения сохраняй с явным статусом и условием удаления в документе задачи.
После подтверждённого применения ко всем выбранным целям и завершения readback
убери одноразовый SQL из operational scripts, если он больше не нужен там.
Если единственный оставшийся потребитель — regression tests, перенеси нужный
SQL в test fixtures существующей suite, обнови пути/ссылки и запусти полную
PostgreSQL suite. Не удаляй проверки ради уборки и не оставляй operational script
бессрочно только из-за тестового пути. Неприменённый пакет не является мусором.

## Публикация и результат

Если старые клиенты отклоняют неизвестный type, отдели поддержку enum/schema
от публикации строки. Определи подтверждаемый порядок mobile release → допуск
клиентов или согласованное решение совместимости → data publication.
Наличие нового checkout или выпуск нового build сами по себе не доказывают
обновление всех пользователей. Не добавляй version gate/новые поля молча.
Если строка уже выдаётся каталогом, зафиксируй текущее влияние на клиентов;
не называй эту публикацию отложенной и не удаляй запись автоматически.

Правила внешних операций, backup и конкретных разрешений бери из
[operations](../grippo-operations/SKILL.md). План, локальная реализация и
идемпотентный SQL не разрешают SSH, live SQL, dump или deploy. Перед разрешённой
операцией сначала подготовь конкретный проверяемый пакет; уже достаточное
разрешение на тот же неизменный шаг не спрашивай повторно.

В отчёте отдельно укажи исходники, подготовленные schema/data changes,
фактическое применение, deploy/client compatibility. Дай ссылки на план и
артефакты, результаты проверок и оставшиеся зависимости. Реальный каталог
готов только после readback в нужной среде и проверки поддерживающего клиента.
