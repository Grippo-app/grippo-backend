# Проверка поведения комплекта

Этот раздел нужен при создании/существенном изменении skill или profiles,
а не для каждого аудита каталога. Структурный validator не измеряет качество
решений. Отдельно проверяются скрипт, поведение инструкций и их интеграция.

## Слепой прогон

Используй [базовые синтетические задания](../assets/audit-cases.json). Их
офлайн-часть проверяет рассуждение по предоставленным фактам; она не проверяет
поиск или чтение реальной статьи. Факты синтетической работы не выдавать за
реальную публикацию. Повторяемый baseline не заменяет новые слепые задания.
В baseline v4 сеть явно разрешена только H05/W85. L27/P38/D46/E52/S63/T74
проверяют владельцев локализации, процентов, сложности, оборудования, синтеза
и план команды; W85 проверяет настоящий многопервоисточный поиск. Это разные
виды покрытия: планирование не доказывает исполнение полного аудита командой.

1. **До запуска** создай receipt с уникальным run_id: точные hashes инструкций
   и назначенных cases, профиль, модель/режим наследования, параметры запуска.
   Ни поздний hash текущего дерева, ни git revision с untracked-файлами не
   доказывают, какие инструкции получил прежний исполнитель. Формат ниже.
2. Новый независимый исполнитель получает SKILL, дословные инструкции
   профиля, назначенные cases и их сырые материалы. Он не получает прежние
   выводы, suspected bug или [ключ оценки](evaluation-rubric.md).
   Не наследуй историю с ожидаемыми решениями, если инструмент позволяет.
3. Исполнитель фиксирует ответы во временном артефакте: решение и его
   основание, предлагаемые изменения/условия, недостающие данные и допустимое
   следующее действие. Зафиксируй hash ответов до передачи grader; добавь в
   receipt agent_id и фактически открытые references/источники. Самоотчёт о
   чтении и наблюдаемая tool trace — разные уровни подтверждения. Оценивание
   не требует точной формулировки ключа.
4. Другой reviewer получает зафиксированные ответы и ключ. Для каждого
   случая отмечает PASS/FAIL/INCONCLUSIVE с конкретным обоснованием.
   Правильное слово без правильного действия не является PASS.
5. Исправь подтверждённый дефект инструкций узко и повтори затронутый случай
   с изменёнными входными деталями. Не добавляй в skill ответ на один кейс.
   Если изменились общие инструкции, повтори все затронутые роли/вопросы;
   отдельный regression не делает остальные старые PASS актуальными.

Один и тот же экземпляр не может одновременно быть слепым исполнителем и
независимым grader. Не поручай автору файла единственное независимое ревью
этого файла. Если роль не загружена клиентом, прогон с переданным текстом
профиля обозначай как проверку инструкций, не доказательство активации.

## Воспроизводимость каждого запуска

Receipt хранится во временном отчёте, без секретов и production rows:

```json
{
  "run_id": "unique-id",
  "started_at": "UTC timestamp recorded before dispatch",
  "profile": "exact-profile-name",
  "instruction_files": {"relative/path": "sha256-before"},
  "cases": [{"id": "case-id", "sha256": "hash-of-exact-assignment"}],
  "launch": {
    "agent_type": "actual-tool-value",
    "fork_turns": "none",
    "model": "inherited; actual model not exposed",
    "overrides": null
  },
  "agent_id": "returned-by-tool",
  "answers_sha256": "recorded-before-grading",
  "opened_references": ["relative/path"],
  "read_evidence": "tool-trace-or-self-report-with-limit",
  "instructions_unchanged_after": true,
  "grader": {"agent_id": "different-agent", "rubric_sha256": "sha256"}
}
```

Можно заранее заморозить весь небольшой skill/profile bundle и затем отметить
прочитанное подмножество; минимально нужны профиль, SKILL, AGENTS и все
доступные исполнителю references, от которых зависит вывод. Зафиксируй также
хэш исходного сообщения/сырых вложений и способ канонизации case JSON.
После ответа повторно сверь hashes; при изменении файла нельзя автоматически
приписать ответ новой версии. Сохрани прежний receipt и повтори затронутую
проверку на стабильных входах. Не дописывай задним числом неизвестные модель,
прочитанные файлы или время запуска. Локальный receipt обеспечивает связь
артефактов, но не является независимой аттестацией всех действий исполнителя.
`fork_turns` берётся из фактического вызова orchestrator, а не из впечатления
исполнителя о видимом контексте. При конфликте metadata сохрани исходные
receipts и отдельную коррекцию с источником достоверного значения; не
перезаписывай raw receipt ради видимости изначально безошибочного запуска.

## Баланс заданий

Кроме распознавания ложных выводов, существенный пересмотр требует новых
заданий без ключа в prompt: обоснованное положительное исправление по
известному канону, конкретная редакционная карта по уже принятому правилу,
корректный APPROVE анализа с честными ограничениями и сверка coverage/counts.
Варианты и числа меняются; точное повторение примера из инструкции оценивается
как baseline, а не перенос навыка на новый случай. Не поощряй blanket refusal:
правильный результат должен завершать доступную полезную часть задачи.

Для проверки researcher отдельно дай первичную ссылку и вопрос **без готового
пересказа результата**. Разреши только чтение источников; зафиксируй реальный
уровень доступа, claim-level ссылку и проверенные методы/исходы. Если источник
недоступен, честное признание может пройти проверку честности, но способность
извлечь результат остаётся INCONCLUSIVE/NOT_RUN. Не подменяй её офлайн-кейсом.
Grader сверяет научные утверждения с первоисточником, а не только с ключом.
После фиксации и оценки новые задания можно включить в baseline для повторных
прогонов. С этого момента они известные regression cases; при следующем
существенном пересмотре подготовь новые независимые holdouts.

## Остальные проверки

- `python3 scripts/validate-agent-kit.py`: metadata, links, routing, inventory.
- `quick_validate.py` из доступного skill-creator: проверка нового SKILL.
- `inspect_snapshot.py`: синтетические корректные/ошибочные входы, exit codes,
  сохранность input hash и отсутствие строк/текстов во внешнем выводе.
- Независимое чтение актуального diff и спорных научных источников.

Не изменяй рабочую БД, не читай SQL-дамп и не устанавливай PostgreSQL для
этой проверки. Подмена valid JSON summary вместо полного snapshot не является
реальным прогоном каталога. Новые постоянные тестовые сервисы не нужны.

В результате раздели baseline, новые holdouts и regressions; укажи для каких
hashes/ролей получен результат, число случаев, полный перечень failures и
limitations: например, полный snapshot отсутствует, нет визуального просмотра
демонстраций, не проверено обнаружение ролей клиентом. Не называй поведенческую
проверку этого набора случаев доказательством общей научной безошибочности.
