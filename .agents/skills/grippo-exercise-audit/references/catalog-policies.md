# Контракты Grippo и решения о правилах каталога

Используй для отделения ошибки данных от научной неопределённости и выбора
продукта. Ни этот файл, ни старый аудит не заменяют текущие `src`, клиентский
код и разрешённый снимок. Факты ниже проверены по локальным исходникам
18 октября 2026; перед новым аудитом перепроверь затронутую реализацию.
Локальное состояние не доказывает такую же ревизию или constraints в production.

## 1. Существующее поведение, подтверждённое исходниками

### Каталог и ссылки

- `ExerciseExamplesEntity` хранит nullable enum-поля категории, типа веса,
  направления и сложности, базовый текст, muscle bundles, equipment refs,
  переводы и отдельную сущность components. Nullable в entity и обязательность
  в create/update DTO — разные уровни контракта.
- `ExerciseExampleRequest` требует непустую карту мышц; каждый процент —
  целое число в `0..100`, сумма карты — `100`. **Ноль разрешён этим DTO.**
  Поэтому нулевая связь может быть редакционным артефактом, но не нарушением
  данного диапазона. Проверка относится к входу через DTO; в entity bundles
  нет CHECK суммы/диапазона. Нельзя объявить существование таких DB constraints
  по одному DTO; схему конкретной БД проверяют отдельно разрешённым способом.
- Сервис `validateReferences` проверяет существование muscle/equipment IDs
  через transaction manager и `for_key_share`. Использование `Set` при поиске
  FK не доказывает запрет повторов в исходном массиве. Дубликаты связей нужно
  обследовать; не утверждай, что текущий контракт гарантирует уникальность.
- `equipmentRefs` может быть пустым. Каждая запись содержит `equipmentId`;
  в ref entity отсутствуют количество, обязательность, группа альтернатив,
  AND/OR. Наличие нескольких refs само по себе не выражает совместную нужду.
- Каталожные create/update могут заменять дочерние записи. Не путай
  семантический минимальный набор изменений с безопасностью полного PUT:
  перед применением нужно проверить фактический путь записи и сохранение
  остальных полей/связей в соответствии с доменным и operations skills.

### Components: отсутствие, необязательность и коэффициент

Публичный DTO содержит все четыре ключа:

| Поле | Текущий допустимый смысл и ограничения |
|---|---|
| `externalWeight` | `null` либо объект `{required:boolean}`. `false` сохраняется как false, не преобразуется в отсутствие. |
| `bodyWeight` | `null` либо `{required:true,multiplier:number}`; multiplier — конечное число `0.05..2.0`. |
| `extraWeight` | `null` либо `{required:boolean}`; непустое значение требует непустого bodyWeight. |
| `assistWeight` | `null` либо `{required:boolean}`; непустое значение требует непустого bodyWeight. |

`externalWeight` исключает `bodyWeight`, `extraWeight`, `assistWeight` даже
при `required:false`. Extra и assist не обязаны исключать друг друга:
оба могут быть доступными необязательными каналами. Само присутствие двух
каналов не доказывает одновременную реальную нагрузку. Текущий validator
также не устанавливает обязательность хотя бы одного ненулевого канала.

Entity сохраняет required-флаги в nullable boolean-полях, multiplier в
`numeric(4,2)`, а сервис восстанавливает публичные объекты по `null`/значению.
Диапазон и совместимость также описаны CHECK в entity. Это описание схемы;
фактическое наличие CHECK в выбранной БД подтверждают отдельно. Не добавляй
к multiplier несуществующее DTO-правило «ровно два знака»: точность хранения
и принимаемое числовое значение — разные вещи.

### Enum и локализация

Текущие значения — продуктовые идентификаторы, а не научно валидированные
шкалы или полный словарь анатомии:

| Измерение | Значения / граница |
|---|---|
| category | `compound`, `isolation` |
| experience | `beginner`, `intermediate`, `advanced`, `pro`; автоматической оценки или обоснованной кодом рубрики нет |
| weightType | `free`, `fixed`, `body_weight`; принудительной связи с набором components в рассмотренном сервисе нет |
| forceType | `push`, `pull`, `hinge`; не всякое движение однозначно исчерпывается этими словами |
| мышцы | Enum включает агрегаты (`calf`, `gluteal`, `hamstrings`, `forearm` и др.), а также части большой грудной; это не одинаковый уровень анатомической детализации |
| оборудование | Enum задаёт поддерживаемые типы; отсутствие типа для нужной опоры не разрешает присвоить случайный похожий |
| языки API | SUPPORTED_LANGUAGES: `en`, `ua`, `ru`, `pt-BR`, `pt-PT`; default `en`. Источник — i18n.types.ts. Не заменяй `ua` на header alias `uk` и не сливай PT локали в один storage code |

Базовые поля и переводы существуют раздельно. `translateExample` выбирает
строку нужного языка либо английскую, затем подставляет базовое поле для
`null` у выбранной строки. Если строка нужного языка существует с одним
пустым полем, для этого поля используется base; это не гарантированная цепочка
«поле locale → поле en → поле base». Проверь все релевантные поля при правке,
не рассчитывай, что fallback скроет противоречивый перевод.

### История и потребители

- `ExercisesEntity` имеет `exerciseExampleId`; запрос отдельной тренировки
  подтягивает **нынешние** bundles и components каталога. Смена карты может
  изменить возвращаемое описание старой тренировки. Не утверждай, что все
  endpoints включают одинаковые relations: проверь конкретный запрос.
- `IterationsEntity` сохраняет собственные `externalWeight`, `bodyWeight`,
  `bodyMultiplier`, `extraWeight`, `assistWeight`, repetitions. Обновление
  каталожного коэффициента не переписывает эти сохранённые поля.
- `TrainingsService` сохраняет переданные клиентом агрегаты exercises/training;
  обновление каталога не запускает пересчёт истории. Отдельные метрики используют
  сохранённые aggregates, другие — веса подходов. В `ExerciseMetricsService`
  расчёт веса использует `external + body × (multiplier ?? 1) + extra − assist`.
  Не выдавай эту программную формулу за физическую силу в суставах.
- Из этого backend нельзя заключить, как мобильный клиент считает мышечный
  объём, отображает коэффициенты, фильтрует weightType или интерпретирует refs.
  Отсутствие доступного клиента — явно незавершённая проверка совместимости.

## 2. Редакционные конвенции: предложение, пока не приняты пользователем

Не представляй перечисленное ниже существующим кодовым контрактом,
научным измерением или разрешением применить правки. Если пользователь уже
принял соответствующее правило в текущей задаче, используй его и ссылку на
решение; повторного утверждения того же правила не требуется.

### Проценты как учётная модель

Рекомендуемый вариант для обсуждения: **условные относительные веса основных
и значимых вторичных целевых групп**, включая целевую изометрическую работу.
Сопутствующие стабилизаторы рассматриваются по функции, а не удаляются по
малому числу. Это один из возможных продуктовых вариантов; другая явно
принятая пользователем модель допустима.

Перед массовым пересмотром установи:

1. Цель процентов: визуализация, распределение учётного объёма, рекомендации
   или другой сценарий; что пользователь увидит и какое решение примет.
2. Включённые роли, знаменатель нормализации и обращение с целевой изометрией.
3. Анатомическую гранулярность: как агрегаты сопоставляются с исследованиями
   отдельных мышц/частей; что делать с не представленными мышцами.
4. Уровень требуемой численной точности и правила неопределённости. Нет
   научного основания для универсального шага 5% или порога удаления ≤3%.
5. Потребителей и историческое поведение: изменение выдачи, сопоставимость
   периодов, необходимость версии/пояснения. Изменение схемы версионирования
   можно предложить отдельно; аудит не добавляет его самостоятельно.

Без этих решений допустимо исправлять доказанные нарушения действующего
контракта в разрешённом scope, предлагать качественные мышечные роли и
показывать неопределённость. Нельзя пересчитать весь каталог «по науке»,
потому что все карты формально дадут 100. `0..100` и сумма 100 — синтаксическая
целостность, не валидность физиологических долей.

Если для практического продукта принята численная редакционная карта,
каждый её процент маркируй как такой вес. Не добавляй псевдоинтервалов
«±2%» и не выдавай совпадение специалистов за измерение. Ранги мышц и
направление различия иногда обоснованы лучше, чем величина разницы.
Проверка интерпретации исследований — по
[exercise-model.md](exercise-model.md).

### Категории, сложность и вариант

Рубрика основных рабочих суставных действий и шкала сложности предложены в
[exercise-model.md](exercise-model.md). Применяй их последовательно к
сравнимым вариантам после принятия правила. Не выводи сложность из числа
мышц или процентов, а категорию — из сложности или известности названия.

Похожие названия и разные карты не доказывают дубликат. Перед унификацией
сверь машину, хват, опоры, ROM, сопротивление и выбранные роли. Если одинаковый
канон подтверждён, единая карта может быть редакционным решением; усреднение
старых чисел не делает её научно точнее. Слияние ID затрагивает историю и не
входит автоматически в задачу правки текста или процентов.

### Оборудование и компоненты

Практичное предложение: refs описывают необходимое оборудование конкретного
канонического варианта. Однако плоский список не умеет выражать альтернативы
и количество. Возможные решения — выбрать один вариант, явно описать
допустимые альтернативы или отдельно спроектировать расширение контракта.
Не выдавай одно из них за уже реализованную семантику AND/OR.

Пустой список не является ошибкой сам по себе. Проверяй противоречие с
описанием: например, обязательная скамья в тексте и отсутствие нужной опоры
в refs. Если нужного типа нет в словаре, результат — предложение изменения
словаря с оценкой enum/API/клиентов, а не подстановка другого тренажёра.
Картинка похожей установки тоже не доказывает доступность этого типа у клиента.

Выбор `weightType` для упражнения с собственной массой и дополнительным
грузом требует согласованного правила и проверки потребителей. Наличие
дополнительного груза само по себе не означает, что основной тип должен
стать `free`; и название `Weighted` не разрешает автоматически сделать
extraWeight обязательным, если канон остаётся общим assisted/unassisted.

## 3. Как фиксировать правило и решение без закрепления старого аудита

Для новой или уже принятой конвенции в отчёте достаточно записать:

`правило → статус (предложено/принято) → источник решения → область →
потребители → исключения/границы → что изменится и что сохранится`.

Сохраняй историю решений конкретной задачи и stable IDs в её артефактах.
Не переносить в системный skill количество упражнений, список прошлых
finding IDs, конкретные карты или спорные уровни как вечную истину.
Исторический пример допустим только с обозначением своего контекста.

Уже принятое человеком решение не требует повторного согласования, если
область и последствия те же. Новые доказательства могут обосновать
пересмотр: покажи, что именно изменилось. Новое правило продукта не даёт
разрешение менять production; действуют scope текущей просьбы и существующие
operations/authorization правила. Отчёт «было → стало» остаётся предложением,
пока применение не поручено пользователем.
