# Протокол review

## Независимость и входные данные

Reviewer получает исходный запрос, критерии готовности, текущий diff, исходное
состояние и результаты проверок. Сам читает нужные источники и места вызова;
авторские выводы не принимает на веру. Самопроверка автора и независимое ревью —
разные проходы. Если второго участника нет, укажи это ограничение прямо.

В режиме review файлы не меняй. Исправляет автор или назначенный implementer;
reviewer затем проверяет исправление на актуальном diff.

## Оси проверки

| Ось | Что проверить по изменённому пути |
|---|---|
| Объём/контракт | Критерии задачи, method/path/status/DTO/response/errors, Swagger, [совместимость старого клиента](../../grippo-architecture/references/conventions.md), доступные consumers; нет посторонних изменений |
| Identity | Проверенный actor, target owner/profile в query, JWT перед admin guard |
| Данные | FK/onDelete/null/default/index, UUID, decimal/hydration, исторические значения |
| Транзакции/конкуренция | Нужные reads/writes через manager, rollback, гонки при count/delete/replacement |
| Запросы | Profile filter, формулы/уровень count, порядок/ties/dates, cardinality/N+1/неограниченные выборки |
| I18n | req.locale, en/ua/ru, фактический fallback/изменение объекта и удаление relations из ответа |
| Интеграции | Claims/signature/audience/expiry, identity linking, timeout/cache/обработка ошибок |
| Эксплуатация | Прямое разрешение каждой попытки, новый штатный dump/source/artifact/storage, без обхода через retry/delegation |
| Секреты | Нет env values, SQL rows, credentials/tokens/keys и чувствительных логов в результатах |
| Поддержка/проверки | Владелец module/DI/локальное оформление, минимальное решение, содержательные проверки и честные ограничения |

Выбирай оси по diff: это не полный аудит backend для каждой правки.
Известный риск важен, если изменение его затрагивает или усугубляет.

## Неопределённый исход записи

При изменении записи или её повторов проверь случай: запись могла завершиться,
а ответ потерян из-за timeout/disconnect. Timeout, отмена HTTP-запроса или
исключение клиента сами по себе не доказывают rollback. Не повторяй запись
автоматически, пока её исход неизвестен и безопасность повтора не установлена.

В разрешённых границах выясни состояние исходной операции по надёжному
operation/resource identity и подтверждению завершения. Немедленное отсутствие
строки или похожая запись не доказывают итог: запрос ещё может выполняться.
Повтор допустим, если операция подтверждённо завершилась без commit и иных
значимых побочных эффектов, либо доказана идемпотентность всей операции или
работает предусмотренная дедупликация. Проверяй children/IDs/history и внешние
эффекты; HTTP method и наличие transaction не доказывают безопасность.
Если подтверждений нет, назови исход неизвестным и предложи диагностический шаг.

Безопасность retry не расширяет объём задачи и разрешения. Для deploy остаются
обязательные gates из deployment-policy; возможность повторить команду их не заменяет.

## Замечание и вердикт

Укажи severity, точный path/line или symbol, условие возникновения,
ожидаемое/наблюдаемое поведение, последствие и подтверждение по исходникам или
воспроизведению. Предположение помечай и называй недостающее доказательство.
Предпочтение оформления без последствия не блокирует. Не угадывай поведение,
зависящее от версии TypeORM/OAuth.

- P0 — немедленная критическая потеря/компрометация в затронутом сценарии.
- P1 — серьёзная функциональная ошибка, безопасность или потеря данных.
- P2 — функциональный дефект либо невыполненное требование.
- P3 — необязательное улучшение.

APPROVE — проверенный объём без открытых блокирующих замечаний, с ограничениями.
REQUEST_CHANGES — применимый незакрытый дефект. BLOCKED — исходных данных/доступа
не хватает для самого review; это не изменение системного goal.
APPROVE не разрешает deploy и не гарантирует весь backend.

После исправления перечитай diff, проверь прежний случай, подтверждения и новые
взаимодействия. Авторское «исправлено» не закрывает замечание. Повтори затронутые
проверки и явно закрой или верни замечание. Новое изменение после APPROVE
требует ревью его объёма. Значимые замечания веди в документе задачи;
отдельный журнал для каждой мелкой правки не нужен.

## Проверка инструкций

Проверяй точные условия применения, ссылки и факты по исходникам, одного
владельца общих правил, отсутствие повторяющихся руководств/устаревших рецептов,
согласованность ролей и различие правила/технического ограничения.

Структурный валидатор проверяет metadata/links/inventory. Решения проверяются
независимыми [сценариями](../../grippo-orchestrator/references/routing.md)
без подсказки ответа. Для эксплуатации включи dump-only, failed backup,
неизвестную цель/fingerprint, сбой/disconnect/retry и уже выданное разрешение
на ту же подготовленную попытку. SSH/dump/deploy ради review Markdown не выполняются.
Обязательные gates:
[deployment-policy](../../grippo-operations/references/deployment-policy.md).
